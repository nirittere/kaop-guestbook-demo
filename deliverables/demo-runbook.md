# KAOP live demo runbook

## Goal

Demonstrate a governed incident workflow and an automated GitHub review in less than 12 minutes. Keep the tour focused on platform controls and evidence.

## Preflight, 20 minutes before the session

1. Start the environment.

   ```bash
   make bootstrap
   make healthy
   make test
   ```

2. Confirm the healthy baseline.

   ```bash
   make verify
   kubectl -n kaop-demo get endpoints redis-master
   ```

   Expected: frontend `2/2`, Redis `1/1`, a Redis endpoint, and no new restarts.

3. Confirm the permission boundary.

   ```bash
   kubectl auth can-i get pods --as=system:serviceaccount:kaop-demo:kaop-investigator -n kaop-demo
   kubectl auth can-i get secrets --as=system:serviceaccount:kaop-demo:kaop-investigator -n kaop-demo
   kubectl auth can-i patch deployments --as=system:serviceaccount:kaop-demo:kaop-investigator -n kaop-demo
   ```

   Expected: `yes`, `no`, `no`.

4. Open direct browser tabs for:

   - KAOP fleet or agent inventory
   - KAOP incident workflow and recent run history
   - Grafana alert rule
   - GitHub repair pull request

5. Confirm the PR remains open and contains the KAOP reviewer comment.

6. Keep a terminal ready in the repository root.

## Live sequence

### 0:00 to 2:00 - Platform inventory

- Show the registered agents and ownership metadata.
- Open the Kubernetes investigator.
- Point out its tools and namespace scope.
- State that it has no Secret access and no write permission.

### 2:00 to 3:30 - Workflow structure

- Open the incident workflow.
- Show the Grafana webhook trigger.
- Show the investigation step and output contract.
- Open run history before triggering the new incident.

### 3:30 to 4:30 - Trigger a real fault

```bash
make incident
```

Explain that the rollout changes the Redis Service selector so it no longer selects Redis. The same rollout couples frontend liveness to Redis readiness, turning the dependency outage into restarts.

### 4:30 to 6:00 - Show Kubernetes evidence

```bash
make verify
kubectl -n kaop-demo logs deployment/guestbook --tail=30
```

Point out:

- Redis has no endpoints.
- The new frontend pod is not Ready.
- Restart count increases.
- Events show failed probes, Killing, and BackOff.
- Logs show Redis connection failures generated by the real application.

### 6:00 to 8:30 - Grafana and KAOP investigation

- Show the alert moving to Pending and Firing.
- Open the automatically triggered KAOP run.
- Read the root cause, evidence, confidence, affected resources, and suggested fix.
- Connect the finding to the visible Service selector mismatch.

### 8:30 to 10:30 - GitHub reviewer

- Open the `fix/redis-service-selector` PR.
- Show the selector correction and the separation of liveness from readiness.
- Show the manifest validation added by the PR.
- Show the KAOP review comment.
- State that the reviewer can comment but cannot push or merge.

### 10:30 to 12:00 - Recovery and audit trail

```bash
make recover
make verify
```

- Show the Redis endpoint returning.
- Show frontend Pods Ready.
- Show the Grafana alert resolving.
- End on the KAOP run record and audit evidence.

## Output contract for the RCA workflow

```json
{
  "root_cause": "string",
  "evidence": ["string"],
  "confidence": "low | medium | high",
  "affected_resources": ["namespace/kind/name"],
  "suggested_fix": "string"
}
```

## Demo guardrails

- Do not expose tokens, webhook secrets, or credential values on screen.
- Do not give the Kubernetes investigator write access.
- Do not merge the repair PR.
- Do not improvise a second incident during the interview.
- Recover before answering extended questions about cluster state.
